# Сборка и запуск на разных платформах

Требуется Go 1.26.5+. Скрипты собирают исходный код в `bin/`; готовые бинарники не хранятся в Git. macOS требует CGO и Apple SDK на Mac. Windows и Linux собираются без CGO.

## macOS

```sh
./scripts/build.sh darwin arm64
# Для Intel:
./scripts/build.sh darwin amd64
```

[Разрешения macOS](macos-permissions.md) выдаются отдельно. Координаты — Quartz logical points; не смешивайте их с физическими Retina-пикселями. Используйте bounds и коэффициенты масштаба из ответов инструментов.

### Несколько окон Terminal

С версии 0.13.3 при совпадающих границах нескольких окон активный Quartz ID уточняется по уникальному заголовку стабильного AX-focused window. После активации фонового приложения AX-цель выбирается заново из свежего списка, а не из сохранённого до активации. Повторная активация и переключение клавишами не выполняются. Итог подтверждается точным ID нужного окна; при одинаковых/неизвестных заголовках и оставшейся неоднозначности управление останавливается. Для диагностики `session_status {"include_recent":true}` возвращает `focus_match` со счётчиками, но без заголовков и содержимого Terminal. Автоматические тесты проверяют правила сопоставления; реальное переключение SSH-окон требует проверки в GUI-сессии macOS.

## Windows

Из PowerShell:

```powershell
.\scripts\build.ps1
# ARM64:
.\scripts\build.ps1 -TargetArch arm64
Copy-Item configs/config.example.json config.json
.\bin\codex-vision-windows-amd64.exe --doctor
```

Для регистрации подставьте абсолютные пути:

```powershell
codex mcp add codex_vision -- "C:\path\codex-vision\bin\codex-vision-windows-amd64.exe" --config "C:\path\codex-vision\config.json"
```

Координаты — физические пиксели виртуального рабочего стола, включая отрицательные начала. Backend проверяет DPI-awareness и отказывает на недоступном/защищённом desktop. UAC и ограничения Windows на фокус не обходятся. Поля macOS Accessibility и macOS app_launch недоступны.

### Захват изображения Windows

С версии 0.13.5 используется top-down 32-bpp `CreateDIBSection` вместо `CreateCompatibleBitmap` + `GetDIBits`. После `BitBlt` вызывается `GdiFlush`, затем пиксели копируются в собственную RGBA-память до удаления DIB. Ошибка старой сборки `GetDIBits incomplete: The operation completed successfully` означает, что число прочитанных строк не совпало с ожидаемым; нулевой last-error не устанавливает причину. Она не доказывает, что Chrome свёрнут или что отказал фокус.

Для проверки на разблокированной Windows с установленным Go: `$env:CODEX_VISION_WINDOWS_INTEGRATION='1'; go test ./internal/platform/windows -run TestNativeObserveIntegration -count=1`. Это read-only тест экрана; его нельзя считать выполненным по результатам кросс-компиляции. После обновления EXE перезапустите MCP-подключение и проверьте `session_status.server.version`.

### Переключение окон Windows

`window_focus` восстанавливает свёрнутое окно через `ShowWindowAsync`, с версии 0.13.6 один раз вызывает `BringWindowToTop` для перекрытого окна, затем при необходимости один раз `SetForegroundWindow`. Общий срок ожидания — до 2 секунд; успех требует точного foreground HWND, а не ненулевого результата API. Между этапами сохраняются проверка desktop, PID/opaque ID и отмена. Реальный запрет Windows не обходится: нет имитации Alt+Tab, подключения чужих input queues или изменения foreground-lock настроек. Topmost-стили чужих окон не меняются. Клики по панели задач остаются ограничены политикой активного окна.

Ошибка содержит признаки запроса восстановления, возврат SetForegroundWindow и наблюдаемый HWND. Она не доказывает точную причину Windows. Потребуется ручная активация, если система или приложение не завершают переключение в пределах ожидания.

Microsoft описывает [асинхронное завершение активации](https://devblogs.microsoft.com/oldnewthing/20161118-00/?p=94745/) и [ограничения SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow). Native-сборка на другой ОС не является проверкой реального переключения на Windows.

## Linux X11

Нужны установленные локально `xrandr`, `xprop`, `xdotool`, ImageMagick `import` и `loginctl`. Сервер сам пакеты не устанавливает.

```sh
./scripts/build.sh
cp configs/config.example.json config.json
./bin/codex-vision-linux-amd64 --doctor
```

Для ARM64 используйте имя `codex-vision-linux-arm64`. Запускайте Codex/MCP из терминала активного разблокированного локального X11 desktop, без `sudo`, SSH и перенаправления X11. `DISPLAY` должен указывать на локальный Unix display, например `:0`, `:0.0` или `unix:0`. Номер не обязательно 0: не задавайте его вручную вместо значения текущей сессии. Поддерживается default screen 0 и RandR-мониторы; отдельные X screens вроде `:0.1` не поддерживаются.

С версии 0.13.0 проверяется **реальная сессия вызывающего процесса** через `loginctl show-session self`: UID процесса, `Type=x11`, `Active=yes`, `Remote=no`, `LockedHint=no`. Если задан `XDG_SESSION_ID`, он должен совпасть; отсутствие переменной не мешает определить сессию через logind. Сервер не использует `auto`, чтобы не подменить SSH/service-сессию чужим графическим входом.

Пустой `Display` в Ubuntu/GDM больше не вызывает безусловный отказ: дополнительно требуются локальный `Seat` и `ActiveSession`, совпадающий с подтверждённой сессией процесса. Это привязка к сессии/seat, а не получение отсутствующего номера X-сервера из logind; доступ к самому локальному DISPLAY по-прежнему требует X11-аутентификации. Если `Display` заполнен, несовпадение запрещено. Заблокированная, удалённая, неактивная, чужая или Wayland-сессия отвергается. `--doctor` показывает метод привязки в `session.binding`; если процесс не относится к desktop-сессии logind, запустите его заново из локального терминала, а не подставляйте чужой `XDG_SESSION_ID`.

Поддерживаются экран/окна, позиция курсора, перемещение, левый/правый/средний и двойной клик, перетаскивание, прокрутка, клавиши, сочетания и Unicode-текст через XTEST/xdotool. Текст передаётся дочернему процессу по stdin, без clipboard, файлов или аргументов с содержимым. Нужна UTF-8 locale; возможности ввода символов зависят от X11/xdotool, а успешная отправка событий не доказывает доставку текста приложению. Вывод диагностик при текстовом вводе считается возможной частичной доставкой и не повторяется автоматически.

Перед вводом проверяются окно, процесс и геометрия; для клика/scroll — окно под курсором, для drag — границы и фокус на шагах пути. После сбоя/отмены сервер пытается отпустить свои кнопки и клавиши отдельным ограниченным по времени вызовом. При focus выполняется одна активация и проверка результата. Это не делает X11 атомарной или изолированной от других локальных X-клиентов средой.

### Включение управления

Конфигурация `configs/config.example.json` остаётся observe. Для управления есть [assist.linux.example.json](../configs/assist.linux.example.json). Перед использованием проверьте и замените `allowed_processes` на точные пути executable нужных приложений (`/proc/PID/exe`), включая фактический runtime браузера, а не только launcher. Пример разрешает лишь текстовый редактор и не даёт доступ ко всем процессам.

У Linux backend пока нет локального диалога подтверждения. Поэтому пример явно задаёт `local_approval:true` и `confirm_each_action:false`: разрешение выдаёт оператор своим локальным конфигом. С `confirm_each_action:true` клики/клавиатура остаются недоступны; сервер не снимает этот запрет сам. `app_launch`, структурные UI-контролы и `ui_fill` на Linux не реализованы; используйте уже открытые приложения и визуальные действия. Отдельный `mouse_drag` доступен в `tool_profile:full`.

Запуск с подготовленным локальным конфигом:

```sh
./bin/codex-vision-linux-amd64 --config /absolute/path/config.linux.local.json
```

Для ручной проверки откройте новый несохранённый документ в разрешённом редакторе. Проверьте focus, один клик, ввод `Тест Linux 123`, стрелки и выделение через Shift, прокрутку, перетаскивание и отказ при смене окна/блокировке. Не сохраняйте поверх существующего файла. Автоматические тесты backend проверяют контракты команд и отказы; они не заменяют проверку Ubuntu/Xorg на реальном устройстве.

### Wayland

Полный Wayland backend **ещё не реализован**. XWayland не даёт доступ ко всем Wayland-окнам. Нужны отдельные ScreenCast/RemoteDesktop portals, PipeWire и явное системное согласие на выбранный экран/ввод; новая X11-реализация этого не добавляет. Не требуется `xhost +`, доступ root или изменение правил безопасности. До реализации portal-backend используйте «Ubuntu on Xorg».

Семантика проверок и команд: [loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html), [xdotool](https://github.com/jordansissel/xdotool/blob/main/xdotool.pod).

## Установка в отдельный каталог

`./scripts/install.sh [каталог]` или `scripts/install.ps1` собирает и копирует программу. Существующий executable не заменяется. Скрипты не добавляют автозапуск, не меняют PATH и не регистрируют MCP сами.

## Mock

```sh
go run ./cmd/codex-vision --mock --config configs/config.example.json
```

Процесс ожидает MCP JSON-RPC по stdin/stdout; его запуск сам по себе не открывает графическое окно. Mock не захватывает реальный экран и не отправляет ввод ОС. Вывод логов идёт в stderr, stdout зарезервирован под MCP.
