# Наблюдение, ожидание и кадры

## Захват и доставка — разные операции

Сервер может локально снимать экран, обновлять preview и сравнивать кадры, не вызывая модель. Модель видит изображение только после явного MCP-запроса. Наблюдение само по себе не запускает агенту новый ход и не разрешает ввод.

`observation_start` возвращает ID наблюдения, первый кадр и необязательный `preview_url`. Ссылка содержит capability доступа к локальному preview; не публикуйте её. После перезапуска сервера нужна новая ссылка.

```json
{"mode":"task","preview":true,"interval_ms":1000}
```

Это аргументы `observation_start`, а не shell-команда. Для `observation_next` передайте полученные `observation_id` и точный `frame.sequence` как `after_sequence`; не увеличивайте номер самостоятельно.

- `task` — режим по умолчанию, остановка при бездействии агента через 120 секунд; агент также должен остановить его после завершения задачи.
- `continuous` — только по запросу пользователя, до явного stop или отключения.
- `pause` временно приостанавливает наблюдение; `resume` возобновляет его.

Кадры хранятся в памяти, истории файлов сервер не создаёт. Preview может показывать полный захват, пока модель получает только рабочую область. Неизменившийся экран даёт ответ без изображения; это не потеря подключения.

## Область внимания и фильтрация

После первого кадра выберите `watch_region` по наблюдаемой геометрии. Область должна содержать данные, необходимые для решения задачи. `ignore_regions` исключает известные нерелевантные участки из сравнения; это не маскирование приватных данных в изображении.

По умолчанию `stability_ms=600`: изменения sampled-пикселей должны сохраняться до публикации. Порог не распознаёт смысл объектов. Постоянные часы и анимация могут создавать значимые изменения; краткое уведомление, наоборот, может не пройти фильтр.

Model-кадры по умолчанию ограничены шириной 768px после обрезки. `model_max_width=0` сохраняет размер; 160–1920 задаёт предел. Для нечитаемой детали запросите конкретный `screen_region`, вместо постоянной передачи большого полного экрана. Сохраняются desktop-границы для пересчёта координат.

Адаптивный захват замедляется при простое. Это сокращает локальную нагрузку; число кадров для модели зависит от явных вызовов и условий доставки.

## Один пакет — один результат

`desktop_batch` принимает ID активного наблюдения, подтверждённый `window_id`, рабочую область и до 12 предсказуемых шагов. Сначала проверяются все шаги, затем они выполняются последовательно с сохранением проверок окна и политики. Повторов, rollback и скрытого Submit нет.

- `wait_for="change"` — по умолчанию: первое устойчивое изменение, подходит для простых UI-переходов.
- `wait_for="response"` — устойчивое собственное изменение, затем ещё одно устойчивое изменение. Это визуальная эвристика, а не доказательство хода соперника.
- `ready_when` — точная метка/роль, наблюдавшаяся через `ui_controls`. AX-условие имеет приоритет над визуальными фазами.

По умолчанию AX-ожидание требует цикл **ready → busy → ready**. Условия отсутствия, дубликатов, неполного дерева и неизвестного enabled не доказывают готовность. Если метаданные недоступны до ввода, может использоваться явно отмеченный visual fallback; `visual_fallback:false` запрещает его. Ошибка фокуса не скрывается fallback-режимом.

`result_mode="auto"` возвращает текст при подтверждённом AX-условии и изображение в остальных успешных визуальных случаях. Текст подтверждает только готовность указанного контрола, не содержимое страницы. Для решения, требующего нового состояния доски, персонажа или документа, задавайте `result_mode="image"`.

Оба инструмента `desktop_batch` и `mouse_action_wait` по умолчанию не возвращают изображения при таймауте. `image_on_timeout=true` явно запрашивает один диагностический кадр. Ожидание ограничено временем; результат не повторяет ввод.

## Что делать после ответа

Поле `continuation.next` помогает избежать повторного снимка:

| Значение | Следующий шаг агента |
| --- | --- |
| `inspect_result` | Прочитать уже полученный кадр; не вызывать `observation_next` без причины |
| `use_ui_result` | Использовать текст готовности, если его достаточно для задачи |
| `waiting` | Ввод уже отправлен; продолжать только ожидание, не повторять действие |
| `stop` | Разобрать ошибку и прекратить ввод |

Если текст не содержит данных для нового решения, нужен один осмысленный запрос изображения. Текстовый ответ не помечает невиденные пиксели просмотренными. Уже доставленные кадры дедуплицируются, а действительно новое состояние остаётся доступным.

## Диагностика и задержки

`diagnostics` включена по умолчанию. При изображении смотрите `frame.diagnostics`, без изображения — `observation.last_detection`:

- `detection_reason` объясняет решение фильтра: например `awaiting_stability`, `below_threshold` или `stable_change`;
- `delivery_reason` и `image_reason` объясняют выдачу кадра, региона или полного контекста;
- raw/stable bounds и доли изменений показывают участок и масштаб изменения sampled-пикселей;
- сравнение после смены контекста может быть невалидным: это не «изменился весь экран».

Диагностика не подписывает участок словами «часы» или «смена покемона». Это выясняет модель по изображению или оператор. `diagnostics=false` убирает метаданные, не меняя захват.

`interaction.timings` и timings пакета измеряют локальные стадии. Они не включают полное время модели и сети и не являются счётчиком токенов. Скорость курсора не равна общей задержке агента. Процент экономии подписки по этим числам вычислить нельзя.
