# Единый цикл работы с интерфейсом

С версии 0.11.0 доступны `desktop_observe` и `desktop_act`. Старые инструменты сохранены. Модель по-прежнему выбирает цель и действия; сервер объединяет наблюдения, связывает действия с увиденным состоянием, локально ждёт и проверяет явные UI-условия. Он не распознаёт правила игры и не определяет качество стратегии самостоятельно.

## 1. Получить состояние

Аргументы `desktop_observe`:

```json
{"include_controls":true,"include_fields":false,"preview":false}
```

Выбирается активное окно и его видимая область. В compact обход контролов по умолчанию отключён: для визуальной игры с клавиатурой достаточно `{}`. Для target_id и поиска UI-предикатов включите `include_controls:true`, как в примере. В full контролы включены по умолчанию; `include_controls:false` отключает их. Выбор сохраняется в следующих view, включая результаты действий; явные `expect`/`ready_when` продолжают читать нужные UI-данные независимо от этой настройки. Инструмент не активирует приложения. Если наблюдения ещё нет, создаётся task-наблюдение; существующее continuous-наблюдение не останавливается и не перезапускается.

Ответ содержит:

- подтверждённое `window`, включая допуск к вводу;
- `view.view_id`, ID наблюдения, область внимания и срок действия;
- до 64 доступных контролов с ролью, подписью, состоянием и геометрией;
- `target_id` для подходящих enabled-контролов из полного дерева;
- максимум один кадр, если есть новая визуальная информация;
- при `include_fields:true` — свежий снимок текстовых полей для `ui_fill_batch`, без существующих значений.

Для формы можно передать `labels:["Name","Email","City"]`. По умолчанию `max_nodes=500`, максимум 1000. Недоступные UI-данные отмечаются явно; Windows/Linux продолжают работать через визуальные координаты. `controls_status.truncated:true` не доказывает отсутствие элементов и не даёт clickable-ссылки на неполный результат.

`watch_region` позволяет выбрать рабочую область. `wait_ms` по умолчанию 0, при ожидании изменения задайте ограниченный long poll. `after_sequence` берётся из возвращённого кадра. `interval_ms` и `min_delivery_ms` применяются только при создании нового наблюдения; существующий stream сохраняет свои настройки. Preview по умолчанию не запускается.

В compact постоянное наблюдение запускается тем же инструментом: `desktop_observe {"mode":"continuous","preview":true}` — только по явному запросу пользователя. По умолчанию `mode:"task"`. Режим работающего stream этим вызовом не меняется: сначала требуется явная остановка. Для расширенных настроек детектора используйте профиль full.

## 2. Выполнить действие и проверить результат

Передавайте реальные ID из ответа, а не строки-примеры:

```json
{
  "view_id":"VIEW_ID_FROM_RESPONSE",
  "steps":[{"action":"click","target_id":"TARGET_ID_FROM_RESPONSE"}],
  "expect":{"title_contains":"Form saved"},
  "result_mode":"auto",
  "wait_ms":5000
}
```

`desktop_act` проверяет окно, процесс и геометрию. Если активно другое окно, по умолчанию разрешена **одна** отдельно авторизованная попытка focus до ввода. `refocus:false` отключает её. Повтор native focus failure, обход recovery guard или клик по панели задач вместо проверки не выполняются.

Перед каждым шагом с `target_id` сервер повторно читает контролы и требует единственного совпадения роли, подписи, enabled и исходных границ. Это краткоживущая **структурная ссылка**, не постоянная native AX-идентичность. Изменившийся или неоднозначный элемент требует нового наблюдения. Ссылки действуют до 60 секунд; заменённый, просроченный или уже использованный view не повторяется.

Для визуальной цели:

```json
{
  "view_id":"VIEW_ID_FROM_RESPONSE",
  "coordinates":"image",
  "steps":[{"action":"click","x":120,"y":80}],
  "wait_for":"change",
  "result_mode":"image"
}
```

В режиме `image` x/y пересчитываются с учётом масштаба и смещения **кадра именно этого view**. Если изображения в нём не было, такие координаты отвергаются. Режим `desktop` по умолчанию принимает абсолютные координаты backend. Для target_id нельзя одновременно задавать ненулевые x/y.

Для 2048 и других действий с одним собственным результатом используйте `wait_for:"change"` (по умолчанию). `response` ждёт две визуальные фазы и нужен только при отдельном ответе после собственного изменения. Он не определяет очередь хода по правилам игры и может дать лишний тайм-аут в одиночной игре. Один ход без изменения поля также может закончиться тайм-аутом: не повторяйте отправленную клавишу автоматически.

После первого кадра можно передать `watch_region` прямо в `desktop_act`: область внимания меняется в том же вызове, без отдельного наблюдения. Регион должен помещаться в окно и `view.capture_bounds`; преобразование image-координат по-прежнему использует исходный кадр view. Если существующий stream захватывает только часть окна, desktop_observe по умолчанию выбирает пересечение, сохраняя этот stream.

Выполняются только заранее предсказуемые шаги, максимум 12. Если следующий выбор зависит от новой страницы, сначала нужен результат предыдущего действия.

## 3. Что считается проверкой

`expect` доступен и в `desktop_act`, и в `desktop_batch`:

| Условие | Пример |
| --- | --- |
| Изменение заголовка | `{"title_contains":"Form saved"}` |
| Появление контрола | `{"control_label":"Saved","control_role":"AXButton"}` |
| Enabled-состояние | `{"control_label":"Continue","enabled":true}` |
| Исчезновение контрола | `{"control_label":"Loading","present":false}` |

Нужно выбрать заголовок **или** контрол. Контроль требует доступных, полных и однозначных UI-метаданных; неизвестный enabled не удовлетворяет запросу enabled. Отсутствие не выводится из неполного дерева. `expect` нельзя комбинировать с `ready_when`.

По умолчанию `require_transition=true`: если условие уже истинно до ввода, сервер отказывается выполнять пакет. `require_transition:false` явно ослабляет проверку до состояния после действия. Совпадение должно сохраняться в течение `settle_ms`.

`verification.matched:true` подтверждает только указанный native UI-предикат. Это не проверка содержимого файла, выполнения команды, правильности чертежа или хода противника. Такие выводы требуют соответствующей проверки результата и/или изображения.

`result_mode=auto` может вернуть текст при выполненном UI-условии. Если для следующего решения нужна новая позиция, персонаж или вид документа, используйте `result_mode=image`. Пиксельное `wait_for=response` остаётся эвристикой, не semantic game detector.

## 4. Продолжить без лишнего кадра

Успешный `desktop_act` сразу прикладывает новый view и доступные UI-ссылки к уже полученному результату. Следующий шаг может использовать его без дополнительного `desktop_observe`. Новое изображение для этого не снимается.

При таймауте или частичной ошибке новый actionable-view не выдаётся. Проверяйте `completed_steps`, `interaction`, `verification` и `continuation`. Отправленные действия не откатываются и не повторяются автоматически. Текстовый таймаут не означает, что клик не был отправлен.

`desktop_observe` нужен, когда состояния действительно недостаточно, ссылка устарела или необходимо дождаться нового события. Подробные cumulative counters доступны через `session_status`/`observation_control status`; единый ответ их не дублирует полностью.

При обычном завершении задачи останавливается только наблюдение: `observation_control action=stop`. Команда `session_stop` — аварийная блокировка всего ввода до локального перезапуска оператором, а не способ закончить ход, партию или ответ ассистента. Промежуточный отчёт о нескольких ходах не завершает порученную игру: агент продолжает до результата, вмешательства пользователя или реальной блокировки. Самостоятельный сброс аварийной блокировки не предусмотрен.

## Ошибки и метрики

Обычные ошибки обработчиков содержат `failure.code`, `next_action` и `retry_action:false`. Например: `stale_reference`, `coordinates_outside_target`, `access_denied`, `focus_unconfirmed`, `ambiguous_target`, `expectation_already_satisfied`. Это рекомендации, а не разрешение на действия. Формат SDK-валидации и специальный `focus_recovery_required` могут отличаться.

`session_status.metrics` показывает число вызовов и ошибок, возвращённых изображений, объём text + raw image bytes и суммарное локальное время. Не сохраняются значения полей, кадры или тексты действий. Это не точное число токенов, стоимость подписки, время модели/сети или число реальных вмешательств человека.

Наблюдения изображения и UI собираются последовательно. `atomic_ui_snapshot:false` подчёркивает, что это не единый атомарный снимок приложения; повторная проверка снижает риск устаревшей цели, но не устраняет вмешательство других процессов того же пользователя.
